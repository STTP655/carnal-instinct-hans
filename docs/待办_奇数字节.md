# 待办：吃掉「奇数字节」字符串（±1 配对方案）

> 背景：本项目用「**原地等长替换**」改资产里的标准 FString（不改 chunk 长度 → 容器块边界与导出表完全不动 → 零崩溃风险）。
> 但 UE 的 FString 编码规则导致**奇数字节原文无法等长写成中文**：

```
ASCII 原文：  [int32 +N][N-1 字节][00]          → 总字节 = N + 4，可为奇数
UTF-16 中文： [int32 -(M+1)][2M 字节][00 00]   → 总字节 = 2M + 6，恒为偶数
```

全量扫描 1014/1002 时，有 **632 次**因这条规则被跳过（例：Jackal Cult Armour 23B、Requires Level 19B）。

## 方案：同一 chunk 内 ±1 配对（总长守恒）

1. 对某 chunk 里所有想改的字符串，**允许长度变化**（中文 + 最少空格填充即可，不必迁就原长度）；
2. 计算这些改动的**长度增量之和 Σ**；
3. 在其中一条串上**调整填充空格数**，把 Σ 归零（中文后多补/少补空格即可，只要该串余量够）；
4. 于是 **chunk 总长度不变** → 容器侧完全不用动；
5. 但 chunk 内部各 export 的尺寸/偏移会变 → 需要用 **Zen 导出表更新**：
   `72 字节/条`（`+0x00 CookedSerialOffset(u64)`、`+0x08 CookedSerialSize(u64)`，链满足 `off[i+1] = off[i] + size[i]`，末端 = `uexp_len - 4`）；
   把每条被改字符串**按偏移归属到对应 export**，自该 export 起累加增量、平移其后所有 export 的 offset。

## 验收标准

1. 修改前后 **chunk 长度完全一致**；
2. 导出表链自洽（末端 = uexp_len-4）；必要时与 retoc to-zen 产物交叉验证导出表区段与 uexp 区段；
3. 容器写回后 utoc 尺寸不变、ucas 仅追加受影响的块；
4. 装进游戏后：目标中文出现、**无崩溃**、其他文本不受影响。

## 其他路线调研结论（已排除）

- UAssetAPI / UAssetGUI：需 .usmap（本机与社区都没有该游戏映射）
- UassetLocalize v1.1：**仅 GUI**、输出 legacy .uasset/.uexp；其 raw 扫描思路（无需 usmap）值得参考，但不直接可用
- Translator++：需重新打包容器，而本项目实测**重打包容器游戏不采用**
- 社区**没有**针对「奇数字节等长」的现成方案；社区正解是「重写整份资产让工具修表」，与本项目的零风险约束不兼容
