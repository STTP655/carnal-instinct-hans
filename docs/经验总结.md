# 经验总结（2026-10 静态汉化之旅）

> 记录这次从「旧结论认为变长不可行」到「对话 + UI 全静态汉化且功能正常」的关键经验，
> 供后续维护/移植到其他 build 时避坑。

---

## 一、最重要的三条认知

1. **「变长必卡死」是错误的归因。** 变长完全可行，失败的是工程实现：容器重建丢了 `ContainerHeader`（引擎看不见）、译文集混入二进制误判条目、中文用 CP936 写 ANSI 槽。
2. **UI 文本能不能翻，取决于它是不是「逻辑键」。** 同一个 locres 里，12,632 条可以翻、1,422 条翻了必坏功能；不是翻译质量问题，是代码把显示文本反读回去做逻辑。
3. **静态方案有硬边界。** 无本地化键的字面量 FText（`Points Available:`、物品提示属性名、解锁弹窗）locres 永远翻不到——旧机器「全中文」是靠 UE4SS 运行时 SetText 钩子，不是纯静态。

## 二、对话层经验（MSL）

| # | 经验 |
|---|---|
| 1 | 只改 Zen 头里唯一一个 `int32 == 导出数据长度`，其余头部字节逐字节保留——离线性验证方法：对比原/新 chunk 的头，差异必须**只有这 1 个 int32** |
| 2 | 中文写 **UTF-16（负长度前缀）**；ANSI 正长度会按 UTF-8 解码 → 乱码 |
| 3 | 译文必须用**安全译文集**（`zh_safe.json`）：只保留 inline FText 文本值/表格文本段，排除内部查找键与二进制误判条目 |
| 4 | **完整重建容器**：`retoc pack-raw` + 原 ContainerHeader chunk + TOC `container_id` 改回原值（`f7353bd047c79eb2`）；否则 `packages:0`，引擎完全看不到补丁容器 |
| 5 | 未改的 chunk 逐字节复制；回读验证 chunk ID 与原包一致 |
| 6 | 部署前离线复核 + 备份；每轮只替换 utoc/ucas，随时可回滚 |

## 三、UI 层经验（locres）

| # | 经验 |
|---|---|
| 1 | 本 build 的 locres 在 **`pakchunk0.pak`**，不在旧文档说的 1013.pak——**先确认自己 build 的 locres 位置** |
| 2 | repak 参数必须与原 pak 完全一致：mount `../../../`、`V11`、`Oodle`、path hash seed（本 build `0x464517FC`） |
| 3 | repak 输出是未加密 index，引擎可正常加载；**打包非确定性**，等价性看「包内 locres SHA」，不看 pak SHA |
| 4 | 四项离线复核（文件清单/其余文件逐字节/locres SHA/参数）通过再部署，不要跳 |
| 5 | 注入方式：`(空ns, 32hex GUID) → 中文`；UMG 内联 FText 运行时先查 locres，查不到回落英文 |

## 四、禁翻规则怎么来的（排查方法论）

1. **分层替换 + 实机验证**：先替换对话容器（功能正常）→ 再加 UI locres（坏）→ 用仓库自己验证过的 2,065 条安全子集（正常）→ 证明坏在 fix1 的额外条目。
2. **分组保护 + 逐类回归**：V1 保护 `E_Menus` → V4 加全部 `/Enums/` 枚举 + `DT_Menu`（环形菜单恢复）→ V5 加逻辑资产文本（攻击仍坏）→ V6 补漏 `/Enumerations/`、`/09_enums/`（攻击恢复）。
3. **全库扫描定位逻辑键**：把 12 个容器全部 `unpack-raw`，检查每个资产 Zen 头部是否含 `Conv_TextToString`/`EqualEqual_TextText`/`TextIsEmpty`/`GetDisplayNameTextByValue`；再建「FText 键 → 所属资产」映射，筛出「逻辑资产里的文本」。
4. **枚举识别要按路径模式**：`/Enums/`、`/Enumerations/`、`/09_enums/`、`E_*`、`enum_*` 全都算——只匹配 `/Enums/` 漏了 108 个枚举（含 `E_InputBufferKey`、`E_MontageAction` 等战斗枚举），直接导致「普通攻击失效」多排查一轮。
5. **失效表现也能定位**：站定攻击坏但跑动攻击正常 → 输入缓冲/蒙太奇枚举被翻；整个环形菜单失效 → `DT_Menu`/`E_Menus` 被翻。

## 五、踩坑清单（按代价排序）

| # | 坑 | 代价 | 教训 |
|---|---|---|---|
| 1 | 补丁容器 `packages:0`（丢 ContainerHeader） | 部署"成功"但游戏无变化 | 重建容器必须带原 ContainerHeader + container_id |
| 2 | 枚举扫描只匹配 `/Enums/` | 多一轮攻击 bug 排查 | 用路径模式全集，别用单一目录 |
| 3 | `DT_Menu` 当成普通显示文本翻译 | 环形菜单失效 | 菜单数据也可能是逻辑键 |
| 4 | 全量 zh.json（含误判条目） | 崩溃 | 用 `zh_safe.json` |
| 5 | CP936 写 ANSI | 乱码 | 中文一律 UTF-16 |
| 6 | 拿 pak 的 SHA 判断打包是否正确 | 误判"打包失败" | 看包内 locres 的 SHA |
| 7 | 认为"UI 全中文"是基线 | 对静态方案预期错位 | 字面量/Slate 文本静态覆盖不到 |
| 8 | 没备份就动游戏文件 | 无 | 每次替换前备份 3 个文件 |

---

## 六、给后续维护者的建议

1. 游戏更新/Steam 校验后，先重新确认：**locres 在哪、容器布局、repak seed** 是否变化；
2. 任何新翻译批次，先跑 `scan_text_logic.py` + `protect_all_enums.py` 重建保护集，再生成 locres；
3. 每次改动只动一层（对话 or UI），实机验证「攻击 + 跑动攻击 + 环形菜单 + 存档 + 属性」五项再加下一层；
4. 想补字面量文本（`Points Available:` 等）时，优先做**控件资产字面量补丁**而不是运行时 mod——能保持纯静态；但必须先在副本上验证序列化长度改动不破坏资产；
5. 想补环形菜单标签只能走运行时钩子（显示层替换，不改逻辑读取的原文）。
